# Экспериментальный набор S3SYNC Corpus v1

Подготовлен для экспериментов с защищённой дельта-синхронизацией. Это входные файлы и воспроизводимые истории изменений. Реализации S3-клиента, криптографии и измеренных результатов производительности в наборе нет.

## 1. Что подготовлено

Основной исходный корпус: **500 178 823 байта — 500,18 МБ, или 477,01 MiB; 264 файла**. МБ здесь означает 1 000 000 байт, MiB — 1 048 576 байт. Дополнительно приложена небольшая настоящая история проекта Zstandard: **121 состояние и 120 последовательных переходов**, исходные файлы проекта занимают 8 427 969 байт. Исходные данные двух частей вместе занимают около 508,61 МБ. Размер внешнего архива для скачивания будет меньше из-за упаковки.

| Часть основного корпуса         | Количество            | Точный объём, байт | Назначение                                                        |
| ------------------------------- | ---------------------:| ------------------:| ----------------------------------------------------------------- |
| JSONL                           | 256 файлов по 512 KiB | 134 217 728        | Группа небольших корректных файлов со структурированными записями |
| SQLite                          | 1 база, 65 536 строк  | 134 553 600        | Большой корректный файл с локальными обновлениями строк           |
| ZIP                             | 3 архива              | 141 760 967        | Уже сжатые файлы, корректно пересобираемые при обновлении         |
| Silesia, выбранные полные файлы | 4 файла               | 89 646 528         | Неизменяемый реальный контроль: текст, PDF и TAR                  |
| **Всего**                       | **264**               | **500 178 823**    |                                                                   |

Достаточность определяется также числом событий, размером групп, повторами, состоянием сети и режимом кеша. На машине с 4 ГБ RAM значительная часть корпуса может обслуживаться из кеша: это нужно явно учитывать при интерпретации результатов.

Все генерируемые данные синтетические, общедоступные и не содержат персональных сведений. Это управляемая нагрузка, а не запись реального поведения пользователей. Реальная Git-история включена отдельным сценарием.

## 3. Контролируемая история: 840 обновлений

| Группа    | Шагов обновления | Что действительно изменяется                                                                      |
| --------- | ----------------:| ------------------------------------------------------------------------------------------------- |
| `jsonl`   | 240              | На каждом шаге заменяются 8 из 256 JSONL-файлов новыми корректными записями; 4 MiB входных файлов |
| `sqlite`  | 240              | Транзакция изменяет 2048 строк базы; объём новых полезных BLOB-данных — 3 MiB                     |
| `zip01`   | 120              | В первом ZIP заменяется один корректный JSONL-элемент объёмом 4 MiB до сжатия                     |
| `zip02`   | 120              | То же для второго ZIP                                                                             |
| `zip03`   | 120              | То же для третьего ZIP                                                                            |
| **Всего** | **840**          | Пять самостоятельных последовательностей                                                          |

JSONL содержит по одной JSON-записи в строке, каждая строка имеет фиксированную длину 512 байт. Псевдослучайные полезные поля уменьшают искусственную выгоду от одинаковых повторяющихся данных. SQLite изменяется через SQL; база закрывается после каждой транзакции и не требует отдельного WAL-файла. ZIP меняется через корректную замену элемента с пересчётом CRC, размеров и центрального каталога; произвольные байты архива не повреждаются. Неизменённые сжатые потоки ZIP копируются без повторного сжатия; порядок элементов и временные поля фиксированы.

Операции находятся в `history/<группа>.jsonl`. Варианты `read_light` добавляют холодное восстановление после каждых 20 записей и в конце; `read_heavy` — после каждой записи. Это порядок событий, не временная трасса: интервалы между событиями и параметры канала задаёт экспериментальный стенд.

Размер логически изменённых данных не равен размеру патча Octodiff и не равен трафику защищённых объектов. Эти величины предстоит измерить отдельно.

## 4. Настоящая история: Zstandard

Источник: [официальный репозиторий meta/zstd](https://github.com/meta/zstd). В папке `natural_zstd` сохранены начальное дерево файлов и 120 двоичных Git-патчей между 121 последовательным состоянием по первой родительской линии. Все объекты зафиксированы полными commit ID в `commits.json`.

- Первое состояние: `e23d0a96164ed0da410c7a3a334b70e56c7ed022`.
- Последнее: `49cf51799ea051457f57243527aa2058f999f005`.
- В первом состоянии: 652 отслеживаемых файла, 8 427 969 байт содержимого.
- Все 120 переходов применены и проверены: полученное Git-дерево каждый раз точно совпало с деревом соответствующего исходного коммита.

Эта часть полезна как независимый сценарий реальных изменений. Она существенно меньше основного корпуса и не заменяет опыт с крупными группами. Небольшие изменения могут не довести политику до полной перезаписи; для стрессового сравнения порогов используются контролируемые последовательности. Git-патчи нужны только для подготовки эталонных версий. Передаваемую в S3 дельту должен заново вычислять наш C#-клиент с Octodiff.

## 5. Как использовать

Распакуйте внешний архив. Внешний ZIP — упаковка для доставки набора, а не единый объект экспериментальной загрузки. Основные входные файлы находятся в `base/`; рабочие копии создаются в `work/`. Скрипты, журналы, контрольные хеши и каталоги `.git` не включаются в измеряемые данные.

Нужен Python 3.12+ со стандартными модулями SQLite/zlib/bz2; для настоящей истории также Git. Подготовительные скрипты создают входные версии до измеряемой синхронизации.

Проверка полученных исходных файлов:

```bash
python3 corpus_tool.py verify
```

Начало JSONL-сценария и первый переход:

```bash
python3 corpus_tool.py reset --group jsonl
python3 corpus_tool.py step --group jsonl --number 1
```

Сначала C#-клиент синхронизирует исходную рабочую группу после `reset`. Затем для каждого шага готовится следующая версия, запускается измеряемая синхронизация и при наличии соответствующего события выполняется холодное восстановление. Шаги применяются строго последовательно. `reset` восстанавливает только подготовленные рабочие файлы выбранной группы; содержимое `base/` остаётся эталоном.

Для других групп замените `jsonl` на `sqlite`, `zip01`, `zip02` или `zip03`. Перед каждым сравнительным прогоном восстанавливаются одинаковые исходные данные, состояние клиента, S3 и начальный сетевой бюджет. Паузы и подготовка версий не должны создавать разные неучтённые условия пополнения бюджета у сравниваемых вариантов. Время генерации тестовых изменений записывается отдельно от времени синхронизации.

Настоящая история, новая рабочая папка:

```bash
python3 natural_tool.py --work work_natural reset
python3 natural_tool.py --work work_natural step --number 1
python3 natural_tool.py --work work_natural verify
```

Далее шаги 2–120. Для нового прогона используйте новую пустую рабочую папку. В C# передавайте только отслеживаемые исходные файлы; `.git` нужен подготовительному инструменту.

Полная повторная проверка контролируемых историй, без S3:

```bash
python3 corpus_tool.py check-history
```

Она применяет все 840 обновлений и проверяет форматы и контрольные хеши через каждые 20 обновлений и в конце группы. Начальные файлы уже приложены; `build` для обычного использования не нужен. Эта команда предназначена для создания новой копии в пустом каталоге и требует доступа к авторскому серверу Silesia.

## 6. Воспроизводимость и уже выполненные проверки

Состав и SHA-256 каждого исходного файла находятся в `manifest.json`. Результаты прогона всех контролируемых историй — в `history_validation.json`. Отдельно повторены первые 20 шагов JSONL, SQLite и ZIP01: полученные байты совпали с первым прогоном. Начальные ZIP проверены двумя независимыми читателями: Python zipfile и unzip. Исходные TAR прочитаны парсером, PDF успешно прочитан строгим PDF-парсером. 

Окружение подготовки: Python 3.12.14, SQLite 3.53.1, zlib 1.3.2. Фиксированы seed и версия генератора. Начальные файлы одинаковы независимо от ОС: их хеши проверяются при распаковке. Бинарные результаты SQL-операций и DEFLATE могут различаться при смене версий библиотек. Для побайтового повторения checkpoint-хешей нужно то же окружение. Для сравнений на VPS следует один раз зафиксировать окружение подготовки и использовать его для всех политик; смена среды означает новую редакцию контролируемой истории. Seed относится исключительно к тестовым данным, а не к ключам и nonce.

## 7. Как исключить преимущество формата при передаче

S3 хранит тело объекта и метаданные. Расширение исходного файла не задаёт отдельную скорость передачи. В нашей системе S3 получает уже защищённый бинарный пакет, поэтому исходный PDF/SQLite/JSONL должен проходить через один и тот же путь загрузки.

Для первого сравнения фиксируем:

- единый формат защищённого объекта и `Content-Type: application/octet-stream`;
- отсутствие дополнительного сжатия клиента и сервера; внутреннее сжатие исходных ZIP сохраняется;
- один и тот же SDK, размер буфера, режим PUT/multipart, параллельность, проверки и политика ретраев;
- одинаковую группировку данных во всех сравниваемых политиках. JSONL-группа — 128 MiB; база — одна группа; каждый ZIP — отдельная группа;
- отдельные колонки для построения дельты, криптографии и сетевой операции.

Для первого опыта можно использовать обычный PUT на пакет и последовательные запросы. Реализации всех политик должны иметь одинаковый режим. Различия размера пакетов после выбора full/delta являются результатом алгоритма, их не нужно искусственно выравнивать.

Свойства исходного содержимого всё равно влияют на дельта-кодирование и восстановление. Это исследуемый фактор, поэтому результаты показываются по группам, без единой цифры «для всех форматов». Объектные размеры, количество запросов, кеш и конкуренция за CPU/диск также фиксируются.
